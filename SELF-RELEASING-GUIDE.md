# Self Releasing Guide

## Overview

A self releasing app is an app where users may modify the code from within the app itself.    
This guide is for architecting an app like that on cloudflare workers offerings.

The architecture relies on a couple of key concepts:
1. The worker has access to a git repo containing it's own code
2. The worker can spin a container on-demand running a coding agent that has access to deploy previews of the same worker
3. A change is deployed as a branch in code and as a preview in the worker
4. The app is split into two parts - the router and the app code. The router only runs on main branch and is incharge of delegating to previews when viewing a branch.

The guiding principal for this setup is to be as self-contained as possible. 
These apps are designed to be self-hosted on your own cloudflare account and used by trusted users. 
As such, convenience trumps robustness and security.  
 
 
## Initial setup

Self releasing cloudflare apps are deployed from the terminal with `pnpm run deploy`. A Workers Paid plan is required. The deploy script:

1. Builds the code.
2. Generates the wrangler configuration per environment/branch so the same code deploys as production or as a fork with a different database. 
3. All resources are provisioned by the wrangler CLI, these are: 
    * **Artifact namespace** - to keep the app code 
    * **D1 database** - for the router and app data
    * **R2 bucket** - for app images
    * **Worker** AI - for planner agents models
    * **Durable** objects - for agent workflows for the planner and builder
    * **Container image** - for the builder container itself
4. Builds the builder container image from its Dockerfile and deploys the Worker with wrangler. The image is pushed to the Cloudflare registry as part of the deploy.
5. Creates the code repository in the Worker's Artifacts namespace and pushes the local repository to it with full history.
6. Sets the Worker secrets.
7. On a first deploy, prompts for the owner's email and password and creates the owner through the api.

Secrets on the Worker:

- `CLOUDFLARE_API_TOKEN`: one token used for everything the router and builder do through the API. It requires the following account permissions:
  - Workers Scripts Edit - to allow the builder to deploy previews and merge, and the router to set secrets on the worker
  - D1 Edit - to allow the builder to fork the production db for a branch, migrate it and delete it
  - AI Gateway Run - to allow the planner and the builder to call claude
  - Workers Containers Edit - a production deploy from the builder applies the builder container's settings
  - Workers R2 Storage Edit - to allow branch images to be deleted by the builder
- `SIGNING_KEY`: used to sign the handoff header on requests passed to the application. Generated by the deploy script.

The planner and the builder's coding agent call Claude through the account's default AI Gateway, authenticated with `CLOUDFLARE_API_TOKEN`. 

The deploy prints the Worker URL. The owner signs in and adds the other household members from within the application.

## Runtime layout

The Worker is one codebase with three parts: router, application, builder. Production runs all three. 
A fork runs as a Preview of the same Worker, and only its application part is used.

The router owns authentication and user management with better-auth, stored in the production D1. It handles every request to the production URL:

Authentication and the build chat are served by the router itself and never proxied.
A branch is addressed by `?branch=<id>` on the page URL; the app keeps the parameter on every navigation, so each tab is on its own branch and a branch link can be shared. 
The router reads it from the request, or else, for everything but a navigation, from the referer: the browser sends the page URL on every same-origin request the page makes, API calls and asset loads alike.
A navigation reads only its own URL, since its referer is the page it left. 
If it is main, the router handles the application request inside the production Worker. Otherwise it proxies the request to the branch's Preview over its public URL.
The Worker uses `global_fetch_strictly_public` so the proxy reaches a same-zone Preview through its URL.

The boundary between router and application is a single request handoff: the router strips the session cookie, attaches the principal (or none, when signed out) and the branch in a handoff header signed with `SIGNING_KEY`, and passes the request on. 
Locally that is a function call into the application; for a branch it is the same request sent over the network to the Preview. 
The application sees an identical request either way and does not know which path it came through.

The application part accepts the principal and branch only from the signed handoff header. A Preview reached directly, without a valid signature, returns an error.
Previews do not inherit production secrets, so they come from the Worker's Preview base config, which Cloudflare gives every Preview: the deploy script puts `SIGNING_KEY` and `BETTER_AUTH_SECRET` there when it generates them (the Preview's database copy holds values the latter sealed) and `CLOUDFLARE_API_TOKEN` when it is given one (the assistant on a branch reaches its model through the gateway with it; a narrower token may be set there by hand), and the app settings put the household secrets there when they are saved. 
The builder sets no secret on a Preview. A secret changed by hand on the Worker is changed in the Preview base config the same way.

A Preview binds its own D1 database.

The frontend is part of the application. Every request runs the Worker first, since only the Worker knows which branch a request belongs to: the page, its routes and the bundle's hashed JS and CSS all go through the handoff, and a branch serves them from the Preview's assets. Main's asset layer would otherwise answer a page path with main's `index.html` and a branch's bundle with its fallback.

The R2 bucket is shared, with a prefix per branch: an object's key is `<branch>/<folder>/<id>`, such as `main/avatars/<file id>`. Any branch can read any object, since a branch database begins as a copy of production's and keeps pointing at production's files, but writes (uploads, changes, deletes) are only allowed under `/<branch>/`; main writes under `/main/`. A file row records the key, the type, who uploaded it and its visibility. Files have no role permissions of their own: the action that stores one is permissioned (a picture, by whether you may edit that member) and says who may see it. A `household` file is served to every signed-in member, a `private` one only to its uploader, and an owner sees every file. The `files.get` procedure serves the bytes: its output is a stream, and a middleware on the application's implementer answers a file stream with the file's headers.

## Router entrypoints

All router routes live under `/api/arch/`. Everything under this prefix is handled by the router in production and never proxied. Public sign-up is disabled; only the owner creates users.

- `/api/arch/auth/*`: better-auth with the admin plugin.
  - Sign in, sign out, session.
  - Linked accounts: a provider whose client is among the household secrets is offered for members to link an account at, never to sign up with. What the provider grants is kept sealed with `BETTER_AUTH_SECRET`. Application code asks for a member's valid access token through `backend/arch-auth/src/app-interface.ts`, the one file of the auth it uses, which serves any provider the same way.
  - `/api/arch/auth/admin/*`: household user management. Create user, list, set role, remove.
- `/api/arch/branches`
  - `GET /api/arch/branches`: list the user's branches, with the branch the request resolved to.
  - `POST /api/arch/branches/:id/merge`: merge the branch. Fails if main has diverged.
  - `DELETE /api/arch/branches/:id`: abandon without merging, same cleanup as a merge.
- `/api/arch/sessions`
  - `GET /api/arch/sessions`: list the user's sessions, newest activity first; every chat message counts as activity. Archiving keeps the last status; the list shows it greyed out. The branch row holds its session id, so a branch view knows which chat to open.
  - `POST /api/arch/sessions`: create a session.
  - `POST /api/arch/sessions/:id/archive`: archive a session that has no deployed branch, whatever its status. Archived sessions are shown instead of the live ones when asked for, readable but not continued. Merged and abandoned sessions are archived automatically, with their branch.
  - `POST /api/arch/sessions/:id/clear`: wipe an archived session's data: the transcript, the builder's state and container snapshot. The row stays with `cleared_at` set, so lists and branches still name it, but there is nothing left to view.
  - `GET /api/arch/sessions/:sessionId/ws`: upgrade to a WebSocket connected to the session's Durable Object, which serves the chat procedures on it (see Build chat protocol). The Durable Object uses the WebSocket Hibernation API so it sleeps while the chat is idle.

Every other path is an application request and goes through the handoff described above.

## Build sessions

The application has a build button that opens a chat. The first message starts a session: a row for the session, a Durable Object holding the conversation, and a planning agent. Opening the chat alone stores nothing.

The planning agent runs inside the Worker as the session's chat agent (Think, on the Agents SDK). It is Claude with three tools that list, read and search the files on main through the Artifacts binding, and with the session's own tools: one records the plan and the change's short name, one starts the build once the member agrees, and one passes the member's words to the builder while a build is under way. It reads what the request needs and turns the request into a plan the builder can execute. It can ask the user clarifying questions, or answer that the change is not possible. A message may carry pictures, PDFs or text files; the planner reads them, and the tool that passes a message to the builder sends the files of that message along.

When the plan is agreed, the planner's tool starts a builder run.

## Build chat protocol

Once a session exists, all communication between the client and the session goes over the WebSocket. The only REST call is creating the session.

The session's Durable Object is a chat agent, and the socket speaks the Agents SDK chat protocol: the client connects with the Agents SDK client, which reconnects on its own, gets the conversation replayed, and streams each turn as it is generated. Each turn carries only the message just sent; the object keeps the conversation. The object's state, the session's phase (planning, building, waiting, deployed, failed, timed out, closed), is synced to every client as it changes.

The conversation holds three kinds of messages: the member's, the planner's replies with the tool calls they made, and the builder's. A builder message is stored on the member's side of the conversation, marked as the builder's in its metadata and prefixed so the planner knows who speaks; the chat shows it as the builder's own bubble. Attachments are moved out of the conversation once the turns that read them are done, and marked as such in place.

A builder run is the session's sub-agent, dispatched by the planner's tool and shown beside that tool call: the run's status, what it is doing now, and every line of what it did (a step, a thought, a tool call, the coding agent's words, or a run of command output), collapsed to the latest line and expandable. The lines are the run's stored chunks, so a reload shows them again. Merges and abandons, started from the branch menu, are runs too, shown at the end of the chat.

## Builder

Starting the builder:

1. Creates a branch row in the production D1. The branch, its Preview and its database share one slug made from the planner's short name for the change, two plain words as a rule (`shopping-list`); a name a branch had before gets a digit (`shopping-list-2`).
2. Mints a write token for the code repository through the Artifacts binding.
3. Starts a container and hands the run to it: the repository token, `CLOUDFLARE_API_TOKEN` for AI Gateway and deployment, and the plan.

The builder's Durable Object runs the work as a sequence of turns in the container, each a step (clone the repository and create the branch from main, install, verify, commit and push, deploy) or a turn of the coding agent. The container harness keeps each turn durable and the object keeps its events as the run's lines, which the session streams into the chat; the run itself is checkpointed after every turn, so an evicted object resumes where it was. Files the member attached, while the plan was made or in a reply, are written into the container's attachments folder, outside the checkout, and named in the agent's prompt for that turn. The agent's model calls leave the container through the harness, which adds the gateway and its credentials outside it. The container never calls the production URL or the Worker.

The builder talks to the planning agent, which talks to the user. Whenever the builder stops for direction it waits. If no answer arrives within 5 minutes the container filesystem is snapshotted and the container shuts down. When the chat continues after a shutdown, the builder starts from the last snapshot with the new information. The container uses the `durable_object` scheduling policy, which snapshots require.

When development is finished the builder:

1. Runs the tests and verifies the build.
2. Commits to the branch. The commit message contains a summary of the changes, the user's request, and the reasoning that led to the changes. The branch is pushed.
3. Clones the production D1 into a new D1 database for the branch (export, create, import), and applies the branch's migrations to it.
4. Deploys the branch as a Preview under the agreed name, with generated configuration binding the branch's database and referencing the already published container image. Sets the Preview secrets.
5. Returns a response to the chat with a link, snapshots, and shuts down.

The link reloads the page on the new branch.

## Branches

The UI has a branch dropdown listing main and the user's open branches. Switching changes which code the router proxies the user to.

On a branch, a side banner warns that data changes made here are not kept when the branch is merged. The build chat is open on the branch with the session's context, so the user can continue asking for changes; each continuation wakes the builder from its snapshot, and a new deploy replaces the Preview.

## Merging

A branch has a merge button. Merging starts a builder container in merge mode, which:

1. Fast-forwards main onto the branch. Branches use regular merge commits, never squash, so fast-forward is possible whenever main has not diverged.
2. Pushes main.
3. Applies the branch's pending migrations to the production D1, then deploys production.
4. Removes the leftovers: the branch's D1 database, the Preview, the objects under the branch's R2 prefix, the branch, the branch row, and the session's snapshot.

Divergence is only checked when merging. If main has diverged, the merge call fails and the frontend shows an Update button in place of merge. It is not an action of its own: clicking it posts a message into the open build chat asking the builder to bring the branch up to date, like any other chat message. Every continuation starts with the builder fetching main; the coding agent merges `origin/main` into the branch, resolving conflicts, and the redeploy reports the new base commit. After it, the frontend shows the merge button again.

## Upstream updates

A deployment's repository began as a push of the upstream repository, (`UPSTREAM` in `@backend/arch-upstream/source`). The repository keeps a branch named `upstream/main` that follows it. The deploy script pushes it beside main when it does not exist yet, at main's commit. The owner's troubleshooting page has a Branches tab: every branch, archived ones on request, with who created it and its session. Its "Check updates" button pulls upstream's `main` into that branch and compares it with main, all in the Worker's memory: it fetches main from the repository and upstream over the public remote without credentials, pushes the `upstream/main` branch with a short-lived token, and says whether main already contains its head.

When it does not, "Merge into a new branch" starts an upstream update from the branch as the check left it, without pulling again. It is a build session like any other with its request and plan written for it, so the build starts without a planner turn: the same two moves the planner makes with its tools, recording a plan and starting the build, made from code. The plan names the commit and says how to merge it: the commit is already in the clone, conflicts are resolved keeping both sides, and upstream's side is taken for files the runner owns. The builder is given that plan like any other and knows nothing more about it. The session's branch has type `upstream-pull`. From there it is a regular build: verify, commit and push, a Preview, follow-ups in the chat, and a merge from the branch menu. One upstream update is open at a time. Upstream changes to `apps/builder/` apply only after the next deploy from a terminal, since deploys from the builder reuse the published image.
