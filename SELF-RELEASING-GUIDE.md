# Matron

## Overview

Matron is a family organizer (or household management) application that is self-releasing. It is designed for technically minded individuals to deploy easily into Cloudflare Workers and let users modify the application in production.

Users can request changes to the application from within the application, and the development processes happen as part of the production workflows.

Matron is a single deployed Worker on Cloudflare but has three distinct parts: a router layer that handles proxying to specific branches of the code, the application layer that handles the code itself, and a builder layer that handles updating and releasing changes to code.

## Initial setup

Matron is deployed from the terminal with `pnpm run deploy`. A Workers Paid plan is required. The deploy script:

1. Builds the code.
2. Generates the wrangler configuration. Configuration is never committed; it is generated at build and deploy time from the environment, so the same code deploys as production or as a fork with a different database. The Worker is told only its name and origin; the database, bucket, Artifacts namespace and repository, and the builder image are named after the Worker. The planner model and the AI Gateway are constants in code for now.
3. Creates the production D1 database and R2 bucket if they do not exist, and applies all pending D1 migrations to the production database.
4. Builds the builder container image from its Dockerfile and deploys the Worker with wrangler. The image is pushed to the Cloudflare registry as part of the deploy.
5. Creates the code repository in the Worker's Artifacts namespace and pushes the local repository to it with full history. Artifacts becomes the only source of truth for code from this point.
6. Sets the Worker secrets.
7. On a first deploy, prompts for the owner's email and password and creates the owner through better-auth's server API with the `owner` role, so the password is hashed by better-auth itself.

Bindings on the Worker: the production D1 database, the R2 bucket, Images, the Artifacts namespace holding the code repository, the builder container, and an email sending binding. Email is optional; without a configured domain the binding exists but sending fails.

Secrets on the Worker:

- `CLOUDFLARE_API_TOKEN`: one token used for everything the router and builder do through the API: creating and deleting D1 databases, deploying and deleting Previews, Artifacts, and AI Gateway runs. The builder receives this token.
- `SIGNING_KEY`: used to sign the handoff header on requests passed to the application. Generated by the deploy script.

The planner and the builder's coding agent call Claude through the account's default AI Gateway, authenticated with `CLOUDFLARE_API_TOKEN`. The gateway is created by its first authenticated request and holds the provider credentials (unified billing, or a stored provider key), set once in the dashboard. No model provider key exists on the Worker. The assistant's model is chosen in the app settings: an Anthropic model, reached through the same gateway with that token so the stored provider key applies, or a Workers AI model, served by the Worker's AI binding. The builder sets the token on each Preview it deploys, so a branch's assistant takes the same route.

The deploy prints the Worker URL. The owner signs in and adds the other household members from within the application.

## Runtime layout

The Worker is one codebase with three parts: router, application, builder. Production runs all three. A fork runs as a Preview of the same Worker, and only its application part is used.

The router owns authentication and user management with better-auth, stored in the production D1. It handles every request to the production URL:

- Authentication and the build chat are served by the router itself and never proxied.
- A branch is addressed by `?branch=<id>` on the page URL; the app keeps the parameter on every navigation, so each tab is on its own branch and a branch link can be shared. The router reads it from the request, or else, for everything but a navigation, from the referer: the browser sends the page URL on every same-origin request the page makes, API calls and asset loads alike. A navigation reads only its own URL, since its referer is the page it left. Absent means main; naming a branch that does not exist or is no longer live answers 404, a "branch does not exist" page for a navigation. If it is main, the router handles the application request inside the production Worker. Otherwise it proxies the request to the branch's Preview over its public URL. The Worker uses `global_fetch_strictly_public` so the proxy reaches a same-zone Preview through its URL.

The boundary between router and application is a single request handoff: the router strips the session cookie, attaches the principal (or none, when signed out) and the branch in a handoff header signed with `SIGNING_KEY`, and passes the request on. Locally that is a function call into the application; for a branch it is the same request sent over the network to the Preview. The application sees an identical request either way and does not know which path it came through.

The application part accepts the principal and branch only from the signed handoff header. A Preview reached directly, without a valid signature, returns an error. Previews do not inherit production secrets, so the builder sets `SIGNING_KEY` and `CLOUDFLARE_API_TOKEN` on each Preview it deploys.

A Preview binds its own D1 database. Images and email are shared with production.

The frontend is part of the application. Every request runs the Worker first, since only the Worker knows which branch a request belongs to: the page, its routes and the bundle's hashed JS and CSS all go through the handoff, and a branch serves them from the Preview's assets. Main's asset layer would otherwise answer a page path with main's `index.html` and a branch's bundle with its fallback.

The R2 bucket is shared, with a prefix per branch: an object's key is `<branch>/<folder>/<id>`, such as `main/avatars/<file id>`. Any branch can read any object, since a branch database begins as a copy of production's and keeps pointing at production's files, but writes (uploads, changes, deletes) are only allowed under `/<branch>/`; main writes under `/main/`. A file row records the key, the type, who uploaded it and its visibility. Files have no role permissions of their own: the action that stores one is permissioned (a picture, by whether you may edit that member) and says who may see it. A `household` file is served to every signed-in member, a `private` one only to its uploader, and an owner sees every file. The `files.get` procedure serves the bytes: its output is a stream, and a middleware on the application's implementer answers a file stream with the file's headers.

## Router entrypoints

All router routes live under `/api/arch/`. Everything under this prefix is handled by the router in production and never proxied. Public sign-up is disabled; only the owner creates users.

- `/api/arch/auth/*`: better-auth with the admin plugin.
  - Sign in, sign out, session.
  - `/api/arch/auth/admin/*`: household user management. Create user, list, set role, remove.
- `/api/arch/branches`
  - `GET /api/arch/branches`: list the user's branches, with the branch the request resolved to.
  - `POST /api/arch/branches/:id/merge`: merge the branch. Fails if main has diverged.
  - `DELETE /api/arch/branches/:id`: abandon without merging, same cleanup as a merge.
- `/api/arch/sessions`
  - `GET /api/arch/sessions`: list the user's sessions, newest activity first; every chat message counts as activity. Archiving keeps the last status; the list shows it greyed out. The branch row holds its session id, so a branch view knows which chat to open.
  - `POST /api/arch/sessions`: create a session.
  - `POST /api/arch/sessions/:id/archive`: archive a session that has no deployed branch, whatever its status. Archived sessions are shown instead of the live ones when asked for, readable but not continued. Merged and abandoned sessions are archived automatically, with their branch.
  - `POST /api/arch/sessions/:id/clear`: wipe an archived session's data: the transcript, the builder's state and container snapshot. The row stays with `cleared_at` set, so lists and branches still name it, but there is nothing left to view.
  - `GET /api/arch/sessions/:sessionId/ws`: upgrade to a WebSocket connected to the session's Durable Object, which serves the chat procedures on it (see Build chat protocol). The Durable Object uses the WebSocket Hibernation API so it sleeps while the chat is idle.

Every other path is an application request and goes through the handoff described above.

## Permissions

Users have one of three roles: `owner`, `admin`, `member`. What each role may do is hardcoded, not stored. Each feature declares its own resource in `src/permissions.ts` with `definePermissions` from `@backend/commons/permissions`: the resource's actions and the actions each role gets. `backend/access/src/registry.ts` lists every feature's definition and builds the roles with better-auth's access control (`better-auth/plugins/access`), which the admin plugin also checks on its own user management routes, on the server and in the browser's auth client.

The resources so far:

- `branch` (router): `view`, `create`, `merge`. `owner` has all three, `admin` has `view, create`, `member` none: a member uses main only; the branch dropdown is hidden and switching is refused.
- `household` (`manage`): the household's members and settings; owners and admins.
- `member` (`view`): the list of members to share with; everyone.
- `task` and `event`: `view`, `create`, `update`, `share`, `remove`; everyone. The object's own rule (its creator, who it is shared with) decides which ones.
- `conversation`: `view`, `create`, `chat`, `rename`, `archive`; everyone, on their own conversations.
- `database` (the assistant's read-only queries): `read` for everyone, `read_router` for owners and admins.

A service action first calls its resource's `require(principal, action)`, then its object rule. Routes and screens only mirror these checks. The owner is created by the deploy script.

## Application

Application routes live under `/api/app/`. The household starts with a calendar, tasks, conversations and an assistant; what else the application does is added by users through build sessions.

- Calendar: events with a title, an all-day span or a time range, a creator, the users it is shared with and, among those, the attendees (everyone shared with, by default). An event may repeat weekly on chosen weekdays or monthly on chosen days of the month, until a day or for a number of times; stopping a repetition keeps the occurrences before that day. Day, week and month views.
- Tasks: a title, an optional description, a creator, the users it is shared with and, among those, the assignees. A task may have a due date and can be completed.
- Conversations: the user's ask sessions and, for builders, their build sessions. An ask session records the branch it was started on and is continued only there: a Preview's database begins as a copy of production, so main's conversations are listed on a branch but cannot be opened, and the Ask button always starts a new one. The chat socket names its branch in the URL, since a socket carries no referer.
- Ask: an assistant on the Agents SDK's Think harness, under the application. Its tools wrap the services the user could use themselves, so the same permissions apply, plus one read-only query on the database: a single SELECT, checked against the tables the user may read (the household's own tables and `user` for everyone; the router's tables for owners and admins only; the `file` table for owners only).
- Settings: a member changes their name, their picture and password, not their email. A picture is stored as a square JPEG under the branch's `avatars` folder; replacing or removing one deletes the file it replaces when the branch wrote it. Owners and admins manage users (add, remove, change roles) and the app settings: the Anthropic model the planner and builder use, and the assistant's model, which is either an Anthropic model or anything the AI Gateway serves.

## Build sessions

The application has a build button that opens a chat. The first message starts a session: a row for the session, a Durable Object holding the chat connection and transcript, and a planning agent. Opening the chat alone stores nothing.

The planning agent runs inside the Worker. It is Claude with three tools that list, read and search the files on main through the Artifacts binding; it reads what the request needs and turns the request into a plan the builder can execute. It can ask the user clarifying questions, or answer that the change is not possible.

When the plan is agreed, the router starts a builder workflow.

## Build chat protocol

Once a session exists, all communication between the client and the session goes over the WebSocket. The only REST call is creating the session.

The session's Durable Object is an Agent (Agents SDK); the client connects with the Agents SDK client, which reconnects on its own. On connect the server replays the transcript from after the frame id named in the `after` query parameter (all of it when absent or unknown), sends one `synced` frame, then sends every new frame live for as long as the socket is open. Connections hibernate between frames.

The client sends one frame type, `send`: `{ type: "send", text }`, a user message. The server stamps the id, timestamp and role, stores it, and broadcasts it to every connection. Blank text or an unknown connection get an `error` frame back.

Every frame has a `type`, a session-unique `id`, and a `ts`. The Durable Object stores every frame but `synced` and `error` in the transcript, in order. Three stored frame types:

- `message`: `{ role, text }`. From the user, `role` is `user` and `text` is what the user typed: requests, answers, plan approval and the update action. From the server, `role` is `planner` or `builder` and `text` is markdown. Plans, questions, deploy links, and failures are all messages.
- `progress`: `{ text, kind? }`. Server to client only: what the planner or builder is doing right now: a step (cloning, building, deploying), a thought, the agent's words, a tool call, or with `kind` `log` a run of command output. The client folds consecutive lines into one entry that shows the latest line and expands to all of them.
- `error`: `{ text }`. Server to client only, not stored.

The builder's Durable Object posts the builder's messages and progress into the session the same way, and the user's replies reach the builder through it.

## Builder

Starting the builder:

1. Creates a branch row in the production D1. The branch, its Preview and its database share one slug made from the planner's short name for the change, two plain words as a rule (`shopping-list`); a name a branch had before gets a digit (`shopping-list-2`).
2. Mints a write token for the code repository through the Artifacts binding.
3. Starts a container and writes the job into it: the repository token, `CLOUDFLARE_API_TOKEN` for AI Gateway and deployment, and the plan.

The builder's Durable Object runs the job as a sequence of turns in the container, each a step (clone the repository and create the branch from main, install, verify, commit and push, deploy) or a turn of the coding agent. The container harness keeps each turn durable and relays its events into the session's chat; the job itself is checkpointed after every turn, so an evicted object resumes where it was. The agent's model calls leave the container through the harness, which adds the gateway and its credentials outside it. The container never calls the production URL or the Worker.

The builder talks to the planning agent, which talks to the user. Whenever the builder stops for direction it waits. If no answer arrives within 5 minutes the container filesystem is snapshotted and the container shuts down. When the chat continues after a shutdown, the builder starts from the last snapshot with the new information. The container uses the `durable_object` scheduling policy, which snapshots require.

When development is finished the builder:

1. Runs the tests and verifies the build.
2. Commits to the branch. The commit message contains a summary of the changes, the user's request, and the reasoning that led to the changes. The branch is pushed.
3. Clones the production D1 into a new D1 database for the branch (export, create, import), and applies the branch's migrations to it.
4. Deploys the branch as a Preview under the agreed name, with generated configuration binding the branch's database and referencing the already published container image. Sets the Preview secrets.
5. Returns a response to the chat with a link, snapshots, and shuts down.

The link reloads the page on the new branch.

## Branches

The UI has a branch dropdown listing main and the user's open branches. Switching changes which code the router proxies the user to.

On a branch, a side banner warns that data changes made here are not kept when the branch is merged. The build chat is open on the branch with the session's context, so the user can continue asking for changes; each continuation wakes the builder from its snapshot, and a new deploy replaces the Preview.

## Merging

A branch has a merge button. Merging starts a builder container in merge mode, which:

1. Fast-forwards main onto the branch. Branches use regular merge commits, never squash, so fast-forward is possible whenever main has not diverged.
2. Pushes main.
3. Applies the branch's pending migrations to the production D1, then deploys production.
4. Removes the leftovers: the branch's D1 database, the Preview, the objects under the branch's R2 prefix, the branch, the branch row, and the session's snapshot.

Divergence is only checked when merging. If main has diverged, the merge call fails and the frontend shows an Update button in place of merge. It is not an action of its own: clicking it posts a message into the open build chat asking the builder to bring the branch up to date, like any other chat message. Every continuation starts with the builder fetching main; the coding agent merges `origin/main` into the branch, resolving conflicts, and the redeploy reports the new base commit. After it, the frontend shows the merge button again.
